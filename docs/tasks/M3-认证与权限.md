# M3-认证与权限

状态：已完成（2026-09-29）
前置：M2 已完成（统一响应与错误出口、Validation、分页、多数据源、Redis 封装、OpenAPI 分组与前端类型生成）。
目标：完成管理员认证、令牌会话与撤销、RBAC 权限解析与权限注解、安全过滤链逐条收紧、初始管理员引导，以及登录页与权限菜单骨架；不实现文件、审计业务，也不实现管理员/角色/菜单/权限的管理接口。
必读：[总计划](../项目总计划.md)、[架构](../架构设计.md)、[需求与范围](../需求与范围.md)、[接口设计规范](../conventions/接口设计规范.md)、[数据库设计规范](../conventions/数据库设计规范.md)、[Java 编码规范](../conventions/Java编码规范.md)、[配置管理规范](../conventions/配置管理规范.md)、[前端编码规范](../conventions/前端编码规范.md)、M2 任务第 5 节 [下一步：M3 任务](M2-后端公共能力.md#5-下一步)。

## 1. 范围与默认值

- 只修改后端 `backend`（`forge-system`、`forge-framework`、`forge-application`）与前端登录、菜单骨架；不实现文件与审计业务。
- 全部接口仍为 `/api/admin/v1/**`；受保护接口使用 `Authorization: Bearer <token>`；认证失败与无权限同样返回 HTTP 200，`body.code` 分别为 401 与 403。
- 首版只有管理员一种身份：不建普通用户表、不提供注册接口、不提供刷新令牌。
- 令牌为不可预测随机值，Redis 只保存摘要与账号会话信息，浏览器保存在后台管理前端的 `sessionStorage`；默认有效期 7200 秒，可配置。
- 登录失败按用户名摘要计数限流，超过阈值返回 429；失败文案不区分“账号不存在”和“密码错误”。
- 权限以数据库为事实来源：M3 不引入权限缓存，每个受保护请求按管理员实时解析权限，因此“权限变化立即生效”不依赖缓存失效；缓存与失效机制随第一个权限写入接口（M5 的管理接口）一起设计，避免为推测需求预建抽象。
- 初始管理员由启动引导创建，用户名与密码来自环境变量，不写入种子 SQL；`sys_admin` 为空且未提供环境变量时启动失败，避免装出一个无法登录的实例。
- 前端本轮只搭登录页、路由守卫、会话存储与权限菜单骨架，视觉样式在用户提供设计后另行调整，不在此阶段定稿。

### 本轮范围边界

- `forge-system` 本轮交付认证与授权链路；**管理员、角色、菜单、权限的管理接口（CRUD）不在本轮**，与 M5 的“账号/角色/菜单”页面一起实现，届时一并补齐权限缓存与失效。
- 该边界与[总计划](../项目总计划.md) M3 交付口径（认证、RBAC、权限注解、菜单及登录页）一致；如需要在本轮追加管理接口，先更新本节与任务表再实施。

## 3. 实际交付

### 后端安全基础设施（T03、T06）

| 位置 | 内容 |
| --- | --- |
| `forge-framework/security` | `AdminTokenService`（32 字节随机令牌、SHA-256 摘要作键名、会话版本撤销）、`LoginAttemptGuard`（按用户名摘要限流）、`BearerTokenAuthenticationFilter`（会话校验 → 账号状态 → 权限 → 安全上下文）、`BearerTokens`（请求头解析）、`AdminAccountDirectory`/`AdminAccountView`（认证端口与账号视图）、`AuthenticatedAdmin`（认证主体）、`AdminToken`/`AdminTokenSession` |
| `forge-framework/security/SecurityConfig` | 无状态过滤链 + `@EnableMethodSecurity`：CORS 预检与配置中的匿名路径放行，`anyRequest().authenticated()`，`PasswordEncoder` 使用 BCrypt |
| `forge-framework/config` | `ForgeSecurityProperties`（`forge.security.*`：令牌有效期、失败次数上限与窗口、超级管理员角色代码、匿名放行路径） |
| `forge-framework/redis` | `ForgeRedisTemplate.increment(key, ttl)`：原子递增并刷新存活时间，供会话版本与失败计数使用 |
| `forge-framework/web/error` | `GlobalExceptionHandler` 新增 `AccessDeniedException` 处理器：方法级拒绝与过滤链拒绝统一写成 403 |

令牌只在签发响应中返回一次；Redis 中只有摘要、账号 ID、会话版本与签发时刻，不保存权限，也不保存令牌明文。撤销采用会话版本递增：退出只删除当前令牌键，停用与改密递增版本使该账号此前签发的全部令牌立即失效，并发登录不会留下可用旧会话。

| 位置 | 内容 |

### 按验收条目对应的实测结论

| 验收点 | 实测证据 |
| --- | --- |
| 登录成功与配置有效期 | `AuthIntegrationTest` 断言 HTTP 200 + code=0、`tokenType=Bearer`、`expiresIn=1800`（测试取值，证明来自 `forge.security.token-ttl-seconds`），并断言会话键的存活时间同为 1800 秒 |
| 令牌只存摘要 | 同一用例断言 Redis 中只有 1 个键、键名形如 `前缀:auth:session:<64 位十六进制摘要>`，且键名不包含令牌明文 |
| 错误密码 / 账号不存在 | 断言都是 HTTP 200 + code=401，且两者响应 message 完全一致，不暴露账号是否存在 |
| 账号停用 | 登录返回 401；已签发令牌在下一次请求返回 401（过滤链按数据库当前状态判定） |
| 退出登录 | 断言退出后原令牌访问 `/auth/me` 返回 401，且 Redis 会话键被删除 |
| 批量撤销 | `AdminTokenService.revokeAllForAdmin`（停用与改密语义）后两个并发登录的旧令牌都返回 401，重新登录签发的新令牌可用 |
| 篡改令牌 | 令牌尾部追加字符后返回 401 |
| 登录限流 | 测试取 `login-max-attempts=3`：连续 3 次失败后，即使使用正确密码也返回 code=429；成功登录后计数清零，历史失败不再触发限流 |
| 依赖故障 | 模拟 Redis 连接失败时受保护请求返回 HTTP 200 + code=503，且响应不含任何业务数据（不降级放行） |
| 未认证与无权限 | 受保护接口未带令牌 401；受 `@PreAuthorize` 保护的探针在无权限时 403、`data` 为 null、不返回业务数据；只有其他权限同样 403（按代码匹配） |
| 权限变更立即生效 | 同一令牌在授予权限后立即 200、解除权限后立即 403，无缓存与等待期 |
| 超级管理员语义 | 未建立任何角色关系时即可访问受权限保护接口，并可见全部菜单 |
| 菜单可见性 | 普通角色只看到已授予菜单，未授予的 `routeKey` 不出现；菜单标识为前端本地路由白名单键 |
| 未知路径不放行 | 未认证访问未知路径 401（不是 404）；带有效令牌访问同一路径 404（框架错误出口） |
| 真实迁移与幂等 | MySQL 8.4 上真实应用迁移；重启显示 `Schema is up to date`，重复启动不重复执行、不覆盖已有管理员 |
| 前端分流 | `request.test.ts` 12 个用例覆盖 HTTP 200 下 code=0/401/403/400 分流、`data.fieldErrors` 读取、协议异常与传输异常；新增用例覆盖令牌注入 |

### 本轮修复与发现的真实缺陷

| 缺陷 | 现象 | 处理 |
| --- | --- | --- |
| `spring.flyway.enabled=false` 不生效 | 初版装配 Flyway 时没有判断该开关，内存库测试仍执行 MySQL 迁移脚本，`UTC_TIMESTAMP` 在 H2 上不存在导致上下文启动失败；此前没有迁移脚本所以一直未被发现 | `FlywayConfig` 增加 `@ConditionalOnProperty(prefix = "spring.flyway", name = "enabled", ...)`，关闭时不再注册 Flyway 组件；配置规范同步记录 |
| 方法级权限拒绝被当成 500 | `@PreAuthorize` 的拒绝发生在 DispatcherServlet 内，不经过过滤链的 `AccessDeniedHandler`，缺少处理器时落入未知异常分支返回 500 | `GlobalExceptionHandler` 增加 `AccessDeniedException` 处理器，写出 403，与过滤链拒绝同一语义 |
| ArchUnit“业务模块互不依赖”规则误报 | 规则的检查对象与禁止依赖两侧包含同一组包，system 出现类之后，它对本模块实体与服务的正常依赖被算成跨模块违规（一次报出 148 条） | 按模块逐个构造规则，禁止依赖集合排除模块自身；对尚无生产类的模块使用 `allowEmptyShould(true)`，避免把“没有类”当成规则失效 |
| 超级管理员看不到菜单 | 菜单可见性只按 `sys_role_menu` 关系查询，初始管理员没有任何关系记录，登录后侧边栏为空 | 菜单与权限共用同一条超级管理员语义：该角色可见全部有效菜单；新增“超级管理员可见全部菜单”用例，并在真实实例上确认返回“概览” |
| 前端依赖目录被安装中断损坏 | 为管理端加入 Vitest 依赖时 `pnpm install` 在删除 `node_modules` 阶段被环境拒绝，随后 `packages/api-client/node_modules/typescript` 等链接失效，类型检查与构建报“找不到模块” | 撤回管理端的 Vitest 依赖改动，使用 `pnpm install --force --offline` 从本地存储重建依赖（315 个包、0 次下载），恢复后类型检查、Lint、用例与构建全部重新通过；锁文件未被改动 |
| 前端登录响应缺令牌未校验 | 生成的类型中 `accessToken` 为可选，直接写入会话会把 `undefined` 存进 `sessionStorage` | 会话 Store 在缺失令牌时按协议异常处理并提示，不保存半截会话 |

- 初始管理员引导的“已有账号不覆盖”在单元用例与真实重启中验证；空库 + 无凭据的启动失败只做单元验证，未在真实库上制造该状态（真实库已有管理员）。
- 本机执行 `pnpm install` 时出现过一次被环境拒绝的删除操作并损坏依赖目录，已按上文重建；该环境现象不属于项目缺陷，但重建依赖后必须重新执行全部前端检查，本轮已重新执行。
