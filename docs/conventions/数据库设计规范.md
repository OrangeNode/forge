# 数据库设计规范

## 1. 数据库、命名与主键

首版使用 MySQL 8.4 LTS、InnoDB、utf8mb4。数据库与表的排序规则必须显式记录；用户名、角色码等唯一键的大小写规则由所属业务确定，避免依赖环境默认值。

表名与字段使用 snake_case，索引命名使用 `uk_表_用途`、`idx_表_用途`，名称遵守数据库长度限制。所有表、业务字段写中文注释。

主键采用有符号 `BIGINT AUTO_INCREMENT`，业务层 Long，对外字符串 ID。禁止默默改用雪花 ID、UUID 或 unsigned BIGINT。

## 2. 公共字段与删除

| 字段 | 默认设计 |
| --- | --- |
| id | BIGINT，主键自增 |
| created_at / updated_at | DATETIME(3)，按 UTC 语义读写 |
| created_by / updated_by | 按需要记录 Long 操作者 ID |
| created_by_type / updated_by_type | 需要区分操作者来源时记录 ADMIN/SYSTEM |
| deleted | 需要逻辑删除的业务主表使用，0 正常、1 已删除 |

不强迫纯关联表拥有所有公共字段，也不以一个庞大 BaseEntity 覆盖所有表。系统任务的操作者使用 SYSTEM 类型及空账号 ID，不假造管理员。

删除规则：

- 管理员账号首版使用启停状态，不开放账号删除流程。
- 业务主表默认逻辑删除；常规查询及明细查询过滤已删除记录。
- 角色与权限等主数据被引用时先阻止删除或在明确业务事务中解除关系，不能默默级联删除业务数据。
- 账号角色、角色菜单等关系记录物理删除；权限的授权关系由菜单关系承载。
- 审计表追加记录，不接受普通修改；按明确保留期限清理。期限与清理任务在 M4 设计，M0 不触发清理。
- 文件配置被历史文件引用时不得删除；文件对象清理由文件模块策略控制，不套用通用逻辑删除即视为对象已删除。

默认唯一业务键在逻辑删除后不回收，例如唯一编码保持占用。需要复用时专门设计数据库级约束及并发测试，不能只做“先查再写”，也不能把 `(业务键, deleted)` 当成可无限删除重建的通用解法。

## 3. 表归属与核心关系

以下为首版逻辑表清单，正式列定义与 SQL 在对应功能阶段补充，M0 不创建数据库。

| 模块 | 表 | 核心关系与约束 |
| --- | --- | --- |
| system | sys_admin | 管理账号独立表；用户名唯一（不区分大小写） |
| system | sys_role | 角色代码唯一 |
| system | sys_menu | parent_id 构造菜单树；`menu_type` 区分目录/页面，`icon` 保存图标标识，路由标识对应前端白名单；`permissions_json` 保存权限代码、中文名称与说明，`perm_codes` 为鉴权查询索引 |
| system | sys_admin_role | 管理员、角色组合唯一 |
| system | sys_role_menu | 角色、菜单组合唯一；菜单可见性，同时决定该角色获得的接口权限 |
| file | file_storage_config | 存储方案代码、版本组合唯一；目标配置版本化 |
| file | file_storage_default | 单一默认指针，引用一个有效配置版本 |
| file | file_record | 指向存储版本；记录对象键、上传身份与文件元数据 |
| audit | audit_login_log | 记录登录尝试、账号、结果与 traceId |
| audit | audit_operation_log | 记录操作、对象、结果与操作者快照 |

M3 已落地的 system 表（迁移脚本 `db/migration/system/V20260930120000__init_system_tables.sql`）：

- 七张表全部创建；`sys_admin` 只做启停、不设 `deleted`，其余三张主数据表使用 `deleted` 逻辑删除，三张关系表物理删除并带 RESTRICT 外键。
- 用户名与角色代码的唯一键显式使用 `utf8mb4_0900_ai_ci`，唯一性不区分大小写；应用层同时把用户名规范化为小写，两边规则一致。
- 时间列统一 `DATETIME(3)` 且按 UTC 语义写入，默认值与种子数据使用 `UTC_TIMESTAMP(3)`。
- 种子只包含超级管理员角色与“概览”菜单：权限行与管理员、角色、菜单、权限的管理接口一起在 M5 新增，不为尚未实现的接口预建权限。
- 超级管理员角色由配置 `forge.security.super-role-code` 识别，解析时拥有全部有效权限与全部有效菜单，因此不需要为它逐条插入关系记录。

M4 与 M5 已落地的其余表：

| 模块 | 表 | 实现要点 |
| --- | --- | --- |
| file | `file_storage_config` | 按 `(code, version)` 版本化；目标变化创建新版本；`access_key`/`secret_key` 保存 AES-GCM 密文；`max_file_size` 与 `allowed_extensions` 是管理员可调的上传策略 |
| file | `file_storage_default` | 固定单行指针（`id = 1`），只影响新上传；外键 RESTRICT 指向配置版本 |
| file | `file_record` | 引用上传时固定的配置版本 ID；保存随机对象键、原始名称、大小、类型与上传者 ID 及名称快照；逻辑删除 |
| audit | `audit_login_log` | 记录用户名、结果（success/failure）、失败原因分类、来源地址与 traceId；只追加 |
| audit | `audit_operation_log` | 记录操作者类型与名称快照、动作、对象、结果 code 与 traceId；只追加，按保留天数清理 |

- M5 迁移 `V20260930130000` 补齐系统管理菜单与 19 个系统权限码；文件与审计模块各自的权限码与其迁移一起维护。
- 2026-09-30 迁移 `V20260930170000` 先把 RBAC 收敛为管理员、角色、菜单三类主数据：`sys_menu` 新增 `perm_codes VARCHAR(512) NULL`（多个代码用英文逗号分隔，全局唯一），删除 `sys_role_permission`，原“权限管理”菜单节点被逻辑删除，其 `system:permission:*` 权限码不再存在。
- 2026-09-30 后续迁移 `V20260930180000` 为 `sys_menu` 增加 `menu_type`、`icon`、`permissions_json`，把原 `sys_permission` 的代码、中文名称、说明迁入所属菜单后删除该表；`perm_codes` 继续作为鉴权快速查询索引，写菜单时与 JSON 中的代码保持一致。
- 权限标识挂在菜单节点上，因此权限解析是“把该管理员可见菜单节点的 `perm_codes` 合并去重”；`sys_role_menu` 同时是可见性与授权的唯一关系表，另加唯一键 `(menu_id, role_id)` 支持按菜单反查授权角色。
- 审计表不建立指向账号表的外键：保存身份快照，账号改名或删除不影响历史记录；文件记录同理保存上传者名称快照，避免文件模块反向依赖账号模块。
- 逻辑删除后唯一键仍占用（角色代码、菜单路由标识重建同名会冲突），与“默认不回收唯一业务键”一致；权限代码由服务层执行跨菜单唯一校验，需要复用时必须先从原菜单移除。

首版只有管理员一种身份，不建立普通用户表；需要面向终端用户的前台时，先补需求、表设计与身份方案，再新增迁移。

菜单可见性与操作授权由同一份配置表达：菜单节点声明接口权限，角色授予该节点即同时获得可见性与权限（2026-09-30 调整，此前两者分开管理）。

example 模块当前不建表，只提供 `GET /hello` 示例接口，用于验证模块装配与统一响应。后续确需业务示例时，先补充本节与 M6 任务，再新增迁移与表定义。

模块内适合使用外键的关系表优先使用 RESTRICT 约束，在业务事务中显式解除引用。跨模块关联使用逻辑 ID 和公开服务校验，不引入跨库外键。审计保存身份快照，不外键依赖随时可变的账号记录。

跨模块不得直接注入其他模块 Mapper 或写其他模块的表。业务模块对附件的引用通过文件公开服务校验。

## 4. 索引与并发

唯一业务键必须数据库唯一约束，应用检查只改善错误提示。并发冲突返回 HTTP 200、body.code=409，不泄漏索引名或 SQL。

分页和常用过滤按实际查询建立组合索引，说明用途，不为每个字段单独建索引。逻辑删除、时间范围、身份与关联字段的组合需随真实 SQL 验证执行计划。

状态变更与可竞争操作使用条件更新、受影响行数或适当锁机制保证结果，不能仅依靠前端禁用按钮。是否需要乐观锁字段由具体用例决定，不全表默认添加。

## 5. 时间与敏感数据

数据库、连接会话及应用统一按 UTC 读写 DATETIME(3)；Java 映射和 API 序列化必须用跨时区用例验证。前端默认展示时区可配置，示例采用 Asia/Shanghai。

密码仅保存安全编码结果，令牌只在 Redis 保存摘要。S3 凭据采用认证加密（如 AES-GCM），主密钥来自运行环境，加密时不复用 nonce；不记录或返回明文。

存储目标一旦被文件引用，不原地改成另一个根目录、endpoint 或 bucket；目标变化创建新版本。目标不变时凭据轮换是独立受控操作，保留审计并验证旧文件仍可读取。

## 6. Flyway 迁移

每个模块将迁移放在 `db/migration/<module>`。应用仅加载已装配模块的目录，只有主库执行迁移。

版本使用全工程唯一 UTC 时间编号，形如 `V20260914090000__init_system_tables.sql`。生成前检查已有版本；若冲突，分配新编号，禁止同时提交重复版本。

中文命名要求用于 Markdown 文档，不强行改变 Flyway 脚本、构建工具或源代码的技术命名。

已发布迁移不可修改，不通过修改历史脚本或 repair 掩盖漂移。空库安装与已有库升级分别验证；失败后的恢复方式写入实际执行任务。已有客户库不通过删除示例历史脚本卸载模块。

权限种子与所属模块迁移一起维护，不用应用每次启动时无条件覆盖客户配置。初始管理员密码通过环境提供，不能写入种子 SQL。

## 7. 多数据源与事务

默认数据源 `master`，`strict=true`。第二数据源通过独立配置示例启用，首版不建设后台连接管理页面。

使用 HikariCP；连接超时、池容量等环境参数在 M1 配置中明确。数据源键来自后端已知配置，不从客户端任意取值。

`@DS` 切换在事务获取连接前完成，单库事务在 Service 边界。跨库读写不因加了注解就具有分布式原子性；首版不引入跨库原子事务承诺。

第二库示例使用隔离测试数据。Flyway 不自动进入客户外接库；需要迁移时，单独明确数据库所有者与任务。

## 8. 验证清单

- 自增主键正常生成，超过 JavaScript 安全整数范围的 ID 能完整往返。
- 账号停用、业务逻辑删除、关系物理删除的行为一致。
- 唯一约束在并发创建时生效，删除后的唯一键策略符合文档。
- UTC 时间在不同时区往返不偏移。
- 空库迁移、增量迁移、校验失败和移除示例的新项目均有对应验证。
- 主库、第二库、未知数据源、单库回滚、代理调用及上下文清理使用真实 MySQL 验证。
