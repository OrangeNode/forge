# 配置管理规范

本规范定义 Orange Forge 的配置边界、命名与校验要求。总计划给出整体约定，规范给出实现规则，任务文档记录执行结果。

## 1. 核心规则

**项目级常量与可调参数先写入配置文件，再在代码中读取；代码里不留可调数值。**

后端统一写入 `backend/forge-application/src/main/resources/application.yaml`，按环境差异写入 `application-<profile>.yaml`。
前端统一写入各应用自己的 `.env.local`（模板 `.env.example`），通过 `import.meta.env` 读取，构建期注入。

反例（禁止）：

~~~java
if ("master".equals(name)) { ... }                       // 数据源名称写死
return UUID.randomUUID().toString();                      // 缺少配置说明的可调行为
@Max(value = 100)                                         // 分页上限写死
response.setHeader("X-Trace-Id", traceId);                // 追踪头名写死
~~~

正例：

~~~java
@ConfigurationProperties(prefix = "forge.datasource")
public class ForgeDataSourceProperties {
    /** 主库在 dynamic-datasource 中注册的数据源名称。 */
    private String primaryName = "master";
}
~~~

## 2. 必须配置化的内容

| 类别 | 示例配置项 | 说明 |
| --- | --- | --- |
| 端口与地址 | `server.port` | 端口冲突时改配置，不改代码、不停其他项目 |
| 数据源 | `spring.datasource.dynamic.*`、`forge.datasource.primary-name` | 连接信息走环境变量；主库名称走配置 |
| 连接池 | `spring.datasource.dynamic.datasource.master.hikari.*` | 池大小与超时按部署环境调整 |
| 迁移 | `spring.flyway.*` | 目录、基线、校验开关 |
| Redis | `spring.data.redis.*` | 库号、超时、连接池 |
| 分页 | `forge.page.*` | 默认页码、默认条数、每页上限 |
| Web 与追踪 | `forge.web.*` | 展示时区、追踪开关、追踪响应头名称 |
| 上传上限 | `spring.servlet.multipart.*` | 应用硬上限，管理员配置不得高于它 |
| API 文档 | `springdoc.*` | 生产默认关闭 |
| 日志级别 | `logging.level.*` | 按包名调整，不改代码 |
| 前端 | `VITE_API_BASE_URL`、`VITE_APP_ENV`、`VITE_DEV_PORT`、`VITE_API_PROXY_TARGET` | 接口地址与开发服务器行为 |

## 3. 留在代码中的不变式

以下内容属于协议或语言层面的事实，**不**做成配置项，避免“改配置就能改变协议”：

- HTTP 状态统一 200，结果通过响应体 `code` 判断。
- 统一响应的四个字段名：`code`、`message`、`data`、`traceId`。
- `code` 的数值语义：0 成功，400/401/403/404/405/409/413/415/429/500/503 表示具体失败。
- 追踪编号的生成方式与长度（由 UUID 决定）。
- 包名、类名、方法名与模块依赖方向。
- 数据库主键类型、UTC 存储约定、逻辑删除字段语义（字段名可配，语义不可配）。

## 4. 命名与结构

- 后端项目级配置统一放在 `forge` 前缀下，按用途分组：`forge.datasource`、`forge.page`、`forge.web`。
- 需要类型化与校验的参数使用 `@ConfigurationProperties`，类名 `Forge<用途>Properties`，放在 framework 的 `config` 包，由 `@ConfigurationPropertiesScan` 注册。
- 单个取值且无需校验的场景可用 `@Value("${key:默认值}")`，但必须给出默认值。
- 配置类使用 `@Validated` + Jakarta 约束表达取值范围，非法配置在启动阶段直接失败，不带病运行。
- 连接信息、密码、密钥只从环境变量或未提交的环境文件读取；配置文件里只允许出现占位符与开发默认值，禁止写入真实凭据。
- 敏感值不得出现在响应、日志或前端包中。

### 绑定方式的选择（实测结论）

优先使用 setter 绑定（字段 + `@Getter`/`@Setter`）。若发现某个字段的覆盖值被静默忽略，
按下面的顺序核对，不要凭直觉认定约束或配置源有问题：

1. **先确认值真的被绑定了**：临时用 `@Value` 直接在字段上注入同一个键做对照。
   `@Value` 能读到而绑定读不到，说明问题在绑定方式，不在配置源。
2. **不要在构造参数上写 `@Value("${...}")`**：构造器绑定不会解析参数上的属性占位符，
   取值会退化为 0 或默认值，现象是“约束莫名失败”或“配置改了没用”。
   构造器绑定应使用 `org.springframework.boot.context.properties.bind.DefaultValue`。
3. **注意增量编译的假象**：改动配置类后如果只跑 `mvn install` 而未 `clean`，
   旧 class 可能被继续使用，测量结果会自相矛盾。核对字节码确认取值已更新，
   例如 `javap -v -classpath target/classes <配置类>`。
4. 仍无法绑定时，先用最小可验证方式（字段级 `@Value`）保证行为正确，并在此登记原因与后续处理。

`forge.page` 已采用字段级 `@Value` 注入：实测该类的 `maxPageSize` 在 setter 绑定与
构造器绑定（含 `@DefaultValue`）下都读不到配置文件与命令行覆盖值，字段级注入可稳定读取，
约束注解同时生效（越界配置启动即失败）。

## 5. 代码读取配置的约束

- 禁止在业务代码里散落配置字符串 Key；同一配置项只能有一处读取入口。
- 配置项变更不得要求改代码：改 `application.yaml` 或环境变量后重启即可生效。
- 需要按环境区分的差异写入 `application-<profile>.yaml`，基线文件只放通用默认值。
- 新增配置项必须同时更新：`application.yaml` 的中文注释、本规范第 2 节表格（若属于新类别）、以及受影响的测试。
- 不是所有取值都值得配置化：仅出现一次且属于实现细节的字面量保持在代码中，避免制造无用途的配置面。

## 6. 前端配置

- 变量名以 `VITE_` 开头，通过 `import.meta.env` 读取，类型声明写在各自应用的 `env.d.ts`。
- 两个应用各自维护 `.env.example` 与 `.env.local`，不共享运行时配置。
- 禁止在代码中写死域名、端口与接口前缀；开发环境用 Vite 代理指向本机后端。
- 新增前端常量的时机与使用它的功能同时进行，不提前声明未被读取的变量。

## 7. 验证要求

- 配置绑定与生效方式必须有测试：使用与 `application.yaml` 不同的取值，证明取值来自配置（参考 `PageRequestPropertiesTest`）。
- 非法配置要能被发现：至少验证一个越界取值在启动阶段失败。
- 结构调整后必须重新执行：后端 `mvnw.cmd -B clean test`、前端 `pnpm run type-check`，并按[本地开发指南](../本地开发指南.md)启动确认。
